# 笔记历史版本（History）设计

日期：2026-11-12 · 状态：待批准

## 一、现状与问题

- `NoteStore.save()` 每次保存前都把「保存前的整篇原文」写进 `data/.history/<笔记id>/`，每篇最多留 20 份（`MAX_HISTORY`），按文件 mtime 淘汰最旧的。
- 前端停笔 0.8 秒就会自动保存，所以 **20 份版本只能覆盖一两分钟的打字**，稍早一点的内容就被挤掉了。
- 没有任何接口或界面能列出、查看或恢复这些版本，现在只能到磁盘目录里手动翻。
- 每次保存都会写一份完全没有区别的快照，比如只改了一个字、反复点保存。

## 二、目标

1. **能找回来**：几分钟前、昨天、上周、几个月前的版本都能找到，而不是只有最近一分钟。
2. **能看懂**：列表按时间分组，标明每一版来自哪种操作（平时编辑、AI 改写、恢复前、AI 计划执行前）；可以预览，也可以和当前内容逐行对比。
3. **能恢复**：一键恢复，恢复本身也可以再撤销（恢复前先存一版）。
4. **不臃肿**：磁盘占用有上限，自动稀疏，打字时不会每秒产生一份。

## 三、非目标

- 不接 git，不做逐段落的修改记录（blame）。
- 不同步历史版本：WebDAV 备份仍然跳过 `.history`，备份快照那一套保持不变。
- 不做手动给版本命名或置顶（以后可以加，数据格式会预留）。
- 被永久删除的笔记，历史版本不提供入口。

## 四、反目标（出现这些就算失败）

- 恢复失败，界面却显示成功；或者恢复把当前内容覆盖掉了，又找不回来。
- 历史版本无限增长，把磁盘写满。
- 自动保存因为写历史版本而明显变慢。
- 路径可以穿越到其他文件，比如版本 ID 里塞 `../`。

## 五、什么时候存一版（核心决策）

快照存的是**「这次保存之前」**的内容，规则如下：

| 触发 | 是否一定存 | 记录的来源 |
|---|---|---|
| 打开笔记后的第一次保存（一次编辑会话的起点） | 一定存 | `edit` |
| 平时自动保存 | 距这篇上一份快照**超过 10 分钟**才存 | `edit` |
| AI 整篇替换 / 插入后的保存 | 一定存 | `ai` |
| 从历史版本恢复 | 一定存（存的是恢复前的内容） | `restore` |
| 从 WebDAV 备份恢复（`restoreFromSnapshot`） | 一定存 | `backup-restore` |
| AI 计划执行（`agent-exec` 调用 `save`） | 一定存 | `agent` |
| 只改分组（`setGroup`） | 不存（沿用现有约定） | — |

另外两条规则：
- **去重**：要存的内容和这篇最近一份快照完全相同（比较哈希值）时跳过。
- **大小上限**：超过 2MB 的笔记不存，沿用现有的 `MAX_VERSION_BYTES`。

实现方式：`save()` 增加一个可选参数 `opts.checkpoint?: "edit" | "ai" | "restore" | "agent"`。
- 带上它就**强制**存一版，并按它记录来源。
- 不带时按 10 分钟间隔判断。
- `POST /api/notes/:id` 的请求体增加可选字段 `checkpoint`，前端在两种情况下发送：打开笔记后的第一次保存，以及 AI 改写后的那次保存。

效果：连续写 30 分钟大约产生 3–4 份版本，而不是 2000 多次保存每次都存。

## 六、保留策略（自动稀疏）

每次写入新快照后，对这一篇做一次稀疏：

- **24 小时内**：全部保留（按 10 分钟间隔，最多约 150 份）。
- **24 小时到 7 天**：每小时留最新的一份。
- **7 天到 90 天**：每天留最新的一份。
- **90 天以上**：每周留最新的一份。
- **兜底**：每篇最多 200 份，或总大小不超过 20MB，超出时从最旧的删。
- 来源为 `restore`、`backup-restore`、`agent` 的版本在 7 天内不参与稀疏，保证「撤销恢复」一定可用。

稀疏只在写入新快照时针对这一篇进行，不另开定时任务。旧笔记的历史会在下次编辑时顺带整理。

## 七、存储格式（兼容现有文件）

- 目录不变：`data/.history/<笔记id>/`。笔记改名或移动后，历史跟着 id 走。
- 文件名：`<时间戳>-<序号>-<随机4位>.<来源>.md`，例如 `20261112T224749-001-ab12.ai.md`。
  - 旧文件名没有 `.<来源>` 部分，一律当作 `edit`。
  - 版本 ID 就是文件名去掉 `.md`。接口用正则 `^[0-9T]+-\d{3}-[0-9a-f]{4}(\.[a-z-]+)?$` 校验，挡住路径穿越。
- 文件内容仍然是当时的**整篇原文**（含 frontmatter），可以直接用编辑器打开。
- 版本时间取原文 frontmatter 里的 `updated`（也就是那份内容最后一次保存的时间），取不到时退回文件名里的时间戳。排序不再依赖文件 mtime，现有实现用 mtime 不可靠，复制文件后 mtime 会变。

## 八、接口

所有接口都沿用现有的本机访问和 CSRF 防护。

| 方法与路径 | 说明 |
|---|---|
| `GET /api/notes/:id/history` | 列出版本：`[{ versionId, at, reason, title, chars, bytes }]`，按时间倒序 |
| `GET /api/notes/:id/history/:versionId` | 单个版本：`{ versionId, at, reason, meta, body }` |
| `POST /api/notes/:id/history/:versionId/restore` | 请求体 `{ baseHash }`；恢复前先强制存一份 `restore` 快照；返回结构和保存接口相同 |
| `POST /api/notes/:id`（已有） | 请求体增加可选字段 `checkpoint` |

**恢复的语义**：
- 恢复**正文、标题、标签**。
- 保留**当前的** `id`、`created`、分组，`updated` 设为现在。分组属于整理动作，不应该被恢复回去，和 `setGroup` 的约定一致。
- `baseHash` 和磁盘上的不一致时返回 409，前端走现有的冲突提示。

## 九、界面

**入口**：编辑页工具栏增加一个「历史版本」图标按钮（时钟图标），快捷键 `Ctrl+Shift+H`。

**历史版本面板**：右侧抽屉，复用备份面板的抽屉样式，分左右两栏。

- **左栏：版本列表**
  - 按「今天 / 昨天 / 11月10日 …」分组。
  - 每行显示时间、来源徽标（编辑 / AI 改写前 / 恢复前 / AI 计划前 / 备份恢复前）和字数变化（如 `+120 / −30`）。
  - 最上面固定一行「当前」。
- **右栏：内容**
  - 两个标签页：「预览」（Markdown 渲染）和「与当前对比」（逐行对比，新增标绿、删除标红，没有改动的长段落自动折叠）。
  - 底部有「恢复到此版本」按钮，点击后需要二次确认。
- **恢复流程**：
  1. 先把当前未保存的修改保存掉（`doSave`），保存失败或有冲突就不恢复。
  2. 调用恢复接口，拿到新内容后重新载入编辑器，相当于现有的 `resolveReload`。
  3. 弹出提示「已恢复到 11月10日 14:32 的版本，恢复前的内容在历史版本里」。
- **窄屏**：抽屉占满全屏，列表和内容改为上下两段。

**逐行对比**：自己实现一个 `web/src/lib/diff.ts`，按行比对、写成纯函数并配单测，不引入依赖。笔记规模（几千行以内）下性能足够。

## 十一、测试

- store：
  - 10 分钟内的连续保存只存一份。
  - 带 `checkpoint` 时强制存。
  - 内容相同时去重。
  - 稀疏策略按时间分层保留（用可注入的 `now` 模拟跨天、跨周）。
  - 来源为恢复的版本 7 天内不被稀疏。
  - 超过数量或大小上限时删最旧的。
  - 旧格式文件名能被正确读取。
- api：
  - 列出版本、读取单个版本。
  - 恢复后正文、标题、标签变回去，分组和 `created` 不变，并且多出一份 `restore` 版本。
  - `baseHash` 不一致时返回 409。
  - 非法版本 ID（包含 `../` 或不符合格式）返回 400。
  - 不存在的笔记或版本返回 404。
- agent-exec：执行计划后有 `agent` 来源的版本；只改分组时依然不写历史（现有测试保留）。
- diff：新增、删除、修改、空文本、完全相同。
- 前端主流程：在浏览器里实际操作一遍，打开、编辑、查看历史、对比、恢复、撤销恢复，并截图核对。
